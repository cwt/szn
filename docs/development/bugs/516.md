# Bug 516 — numeric choice options are unsettable

### 516. `coerceValue` never converts a `.number` into a `.choice`
**Severity:** MEDIUM
**Status:** ✅ FIXED
**Files:** [`src/options.zig:152-167`](https://github.com/cwt/szn/blob/main/src/options.zig#L152-L167), [`src/cfg.zig:256-260`](https://github.com/cwt/szn/blob/main/src/cfg.zig#L256-L260), [`src/options.zig:99`](https://github.com/cwt/szn/blob/main/src/options.zig#L99)

## Problem

The config/command layer turns any bare numeric token into a `.number`:

```zig
// src/cfg.zig:256-260
if (s.len > 0 and (s[0] == '-' or std.ascii.isDigit(s[0]))) {
    if (std.fmt.parseInt(i64, s, 10)) |n| return OptionValue{ .number = n };
}
```

`Options.coerceValue` is supposed to normalise that against the definition, but
its `.choice` arm has no `.number` case:

```zig
// src/options.zig:152-167
.choice => {
    switch (value) {
        .flag => |b| return OptionValue{ .choice = if (b) "on" else "off" },
        .string => |s| {
            if (def.choices) |choices| {
                for (choices) |c| {
                    if (std.mem.eql(u8, s, c)) return OptionValue{ .choice = s };
                }
            }
            return value;
        },
        else => return value,   // .number arrives here unchanged
    }
},
```

`Options.set` then runs `try validateType(def, coerced)` (`options.zig:99`) with a
`.number` payload against a `.choice` definition and rejects it.

Consequences:

* `status` documents choices `2|3|4|5` (`options.zig:243`) — all four are
  rejected, so a multi-line status bar cannot be configured.
* `clock-mode-style` documents choices `"12"` / `"24"` (`options.zig:292`) —
  both are bare digits, so the parser always produces `.number` and the option
  is **completely unsettable** through either the config file or `set-option`.
* The same class blocks bare numeric colour values (`status-fg 5`).

## Proposed Fix

In the `.choice` arm, format a `.number` to its decimal string and match it
against `def.choices`, returning a `.choice` on a hit and an explicit
`error.InvalidChoice` on a miss (rather than silently passing the wrong tag
through to `validateType`):

```zig
.number => |n| {
    var buf: [24]u8 = undefined;
    const s = std.fmt.bufPrint(&buf, "{d}", .{n}) catch return error.InvalidChoice;
    if (def.choices) |choices| {
        for (choices) |c| if (std.mem.eql(u8, s, c)) return OptionValue{ .choice = s };
    }
    return error.InvalidChoice;
},
```

## Fix

```zig
// src/options.zig — coerceValue, .choice arm
.number => |n| {
    var buf: [24]u8 = undefined;
    const s = std.fmt.bufPrint(&buf, "{d}", .{n}) catch return value;
    if (def.choices) |choices| {
        for (choices) |c| {
            if (std.mem.eql(u8, s, c)) return OptionValue{ .choice = s };
        }
    }
    return value;
},
```

A numeric value is now formatted to its decimal string and matched against the
definition's choices, exactly as the `.string` arm already did. A value outside
the set still falls through unchanged, so `validateType` rejects it as before —
this only makes the *valid* numeric choices reachable.

## Regression test

`numeric-valued choice options are settable — bug #516` (`src/cmd/cmd.zig`)
asserts `set-option -g status 2` and `set-option -g clock-mode-style 24` both
succeed, and that `set-option -g status 9` is still rejected. Before the fix the
first two returned `.err`.

Verified with the full suite on **Zig 0.16.0 and 0.17.0**: 1054/1054 passing on
both.
