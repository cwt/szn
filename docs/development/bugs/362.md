# Bug 362 — UAF window: stale poll events after session teardown in one batch

### 362. The guard itself dereferences freed memory
**File:** `src/server/server.zig:552-557`, `src/server/server.zig:667-671`
**Severity:** HIGH
**Status:** 🔴 OPEN

### Problem
One `pollOnce` batch may contain multiple pty events. If an earlier event's
dispatch runs a command that kills the session (`session.deinit` →
`arena.deinit()`), later events in the same batch still hold `udata` pointing
into the freed arena:

```zig
var pane: *Pane = @ptrCast(@alignCast(ev.udata orelse return .not_ours));
if (!self.isPaneValid(pane)) {      // ← reads pane.valid from freed memory
```

If the allocator reused/unmapped the page, `valid` is garbage and the pane gets
fully processed. Mitigations reduce but don't eliminate exposure:
killSession removes pty fds first (server.zig:2969-2975), but events already
dequeued aren't retroactively cancelled. The per-byte re-resolution fix for
processInput (bug #282, server.zig:1282-1290) has no analogue here.

### Fix (proposed)
Generation counter: stamp each loop registration (and each Pane) with the
current session generation; `handlePtyEvent` compares against the live
generation before touching the pointer. Alternatively abort processing of the
remaining batch entries after any teardown.
