# Bug 511 — resize-pane never updates the layout tree

### 511. `resize-pane` resizes the pane grid but not the layout rectangle that renders it
**Severity:** HIGH
**Status:** ⬜ OPEN
**Files:** [`src/cmd/cmd.zig:1221`](https://github.com/cwt/szn/blob/main/src/cmd/cmd.zig#L1221), [`src/layout.zig:173`](https://github.com/cwt/szn/blob/main/src/layout.zig#L173), [`src/window.zig:387-417`](https://github.com/cwt/szn/blob/main/src/window.zig#L387-L417), [`src/server/render.zig:289-351`](https://github.com/cwt/szn/blob/main/src/server/render.zig#L289-L351)

## Problem

`cmdResizePane` computes a target size and then does exactly one thing with it:

```zig
// src/cmd/cmd.zig:1221
pane.resizeTerminal(target_w, target_h) catch return .err;
window.invalidateBorderFormat();
return .ok;
```

The layout tree is untouched. `Layout.proportion` is assigned in **exactly one
place** — split creation:

```zig
// src/layout.zig:173
.proportion = prop,
```

Every other reference in the tree is a *read* (`window.zig:405,409`,
`render.zig:466,486`, `server.zig:2194,2200,2298,2309`, `layout.zig:268,274`).
There is no `setProportion` / resize API on `Layout`.

That matters because the tree, not the pane grid, is the source of truth for
geometry:

* **Rendering** derives each pane's rectangle from the tree
  (`collectPaneBounds` → `splitSizes(lw -| 1, s.proportion)`) and copies only
  `pb.w × pb.h` cells into the merged screen (`render.zig:289-351`).
* **`Window.resizeNode`** walks the same tree and calls
  `pane.resizeTerminal(frame.lw, frame.lh)` from `splitSizes(...)`
  (`window.zig:387-417`).

So after `resize-pane -R 10`:

| Action | Observed effect |
|---|---|
| Grow the pane | Nothing — the renderer still clips to the old tree rectangle |
| Shrink the pane | The tail of the pane goes blank (`x < cls.items.len` fails → `Cell.empty()`) |
| Any later `Window.resize` | Reverts the grid entirely, because it is recomputed from `proportion` |

`server.zig:1179` has the same shape for the `resize_left/right/up/down`
actions, so those are equally ineffective.

## Why this is filed rather than assumed intentional

The layout tree is the single source of truth for pane geometry everywhere else
in the codebase, and `resize-pane` is a user-facing command documented in
`README.md` and `docs/build-run.md`. Bugs #220 (`swap_pane_*` not resizing
panes) and #284 (`cmdRotateWindow` rotating the pane list but not the tree)
are the same class and were both fixed by making the tree follow — this is the
remaining member of that family.

## Proposed Fix

Give `Layout` a real resize operation: walk to the target leaf's parent `Split`,
adjust `s.proportion` (clamped so both children stay ≥ 1 cell), then re-run the
existing `Window.resizeNode`. `cmdResizePane` and the `resize_*` actions should
call that instead of `pane.resizeTerminal` directly. Explicit `-x`/`-y` sizes
need a different treatment (they do not map onto a single proportion) and may
need to become a no-op or a documented limitation.
