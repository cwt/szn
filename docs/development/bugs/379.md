# Bug 379 — Bare click in copy-mode exits the mode and litters buffers

### 379. Missing movement guard on the copy-mode click path
**File:** `src/server/server.zig:1637-1641` (press), `src/server/server.zig:1662-1671` (release)
**Severity:** MEDIUM
**Status:** ✅ FIXED

### Fix (applied)
The copy-mode press handler records the anchor press coords
(`Server.copy_click_x/y`); on release, a release at the same screen coords is
treated as a bare click — the zero-extent selection is dropped and copy-mode
stays active, no buffer pushed. Releases that moved (or keyboard-initiated
selections with no recorded press) keep the old yank-and-exit behaviour.

**Test:** `bare click in copy-mode stays in mode, drag still yanks — bug #379`
(press/release at identical coords keeps mode + buffer count; press/release
across cells yanks one buffer and exits).

### Problem
- Press: `if (!cm.selection.active) cm.startSelection();`
- Release: `if (cm.selection.active) { yank…; pane.screen.copy_mode = null; }`

A bare click starts a zero-extent selection, then release yanks it (a single
character or empty string after the trailing-space trim at mode_copy.zig:384-386)
onto the paste-buffer stack and kicks the user out of copy mode.

### Fix (proposed)
On release require actual movement since press (compare cursor_x/y at press,
stored alongside start_scroll_offset) before yank+exit; a no-move release
should just clear the selection highlight and stay in copy-mode.
