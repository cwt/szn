# Bug 388 — Escape-parser fidelity cluster

### 388. Five parser fidelity gaps
**Severity:** LOW
**Status:** ✅ FIXED

### Fix (applied)
| Item | Change |
|------|--------|
| a | 8-bit C1 dispatch: IND/NEL (0x84/0x85) and RI (0x8D) execute their controls instead of blanket-entering `.esc` and swallowing the next byte; 0x9D now enters OSC state (it is 8-bit OSC, not PM). |
| b | Sixel `ESC ESC \`: a second ESC while in `dcs_sixel_esc` stays pending, so the real terminator still terminates. |
| c | CAN (0x18) and SUB (0x1A) abort any active escape/CSI/OSC/DCS sequence immediately and transition the parser back to `.ground` per VT500/ECMA-48 spec. |
| d | XTSMGRAPHICS only replies "supported" for Ps1=1/2; unknown probes get silence. |
| e | CSI param table widened 16 → 32 so legal long SGR chains apply their trailing entries. |

**Tests:** Verified with comprehensive unit tests in `src/input.zig` covering all 5 items.

| # | Site | Finding |
|---|------|---------|
| a | input.zig:204-208,217 | All of 0x80–0x8F blanket-mapped to "ESC introducer": IND (0x84), NEL (0x85), HTS (0x88), RI (0x8D) lose their meaning and swallow the next byte as an ESC final (e.g. `0x85 'A'` deletes the A). 0x9D is OSC but routed to sos_pm_apc_string — 8-bit OSC titles discarded until ST. Rare on UTF-8 terminals; wrong nonetheless. |
| b | input.zig:489-503 | `ESC ESC \` inside a sixel payload: first ESC enters dcs_sixel_esc; second ESC appended as payload along with following `\`, so the genuine ST is consumed as data and the image swallows stream bytes until another terminator. |
| c | input.zig:344 | CAN/SUB inside OSC strings absorbed as content instead of aborting per VT spec (companion to #377). |
| d | input.zig:105-117 | Param storage caps at 16; beyond that values accumulate into param_val then vanish — long SGR chains partially applied silently. |
| e | input.zig:697-707 | XTSMGRAPHICS replies `\x1b[?{ps1};0;0S` ("supported, unlimited") for *any* Ps1 including unknown ones — false positives for probing apps. |
