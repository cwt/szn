# Bug 487 — runServerDaemon closes fd 0 twice

### 487. `open("/dev/null")` returns fd 0, then `close(dev_null)` closes stdin
**Severity:** HIGH (daemon ends up with fd 0 closed)
**Status:** 🟠 OPEN
**Files:** [`src/main.zig:438-446`](../../../src/main.zig)

## Problem

```zig
_ = c.close(0);
_ = c.close(1);
_ = c.close(2);
const dev_null = c.open("/dev/null", c.O.RDWR, 0); // == 0, deterministically
...
_ = c.dup2(dev_null, 0); // no-op
_ = c.dup2(dev_null, 1);
_ = c.dup2(dev_null, 2);
_ = c.close(dev_null);    // closes fd 0 again!
```

After closing 0/1/2, `open` deterministically returns the lowest free fd — **0**. The `dup2(dev_null, 0)` is then a no-op, and `close(dev_null)` closes fd 0 a second time. The daemonized server runs its whole lifetime with **stdin closed**. Any later `open()` returns fd 0, so a file opened by server code can alias fd 0 and reads/writes intended for stdin (or that file) go to the wrong place.

## Proposed Fix

Only close when it's actually a spare fd:

```zig
if (dev_null > 2) _ = c.close(dev_null);
```

Or open `/dev/null` three times / use `fcntl(F_DUPFD, 3)` semantics. A regression test can assert fds 0/1/2 are all open and distinct after daemonization.
