# Bug 521 — use-after-free reading the reader buffer during detach

### 521. `processInput` reads freed `MessageReader.buf` after a detach binding
**Severity:** HIGH
**Status:** ⬜ OPEN (unverified — needs a runtime repro)
**Files:** [`src/server/server.zig:2592-2597`](https://github.com/cwt/szn/blob/main/src/server/server.zig#L2592-L2597), [`src/server/server.zig:1135`](https://github.com/cwt/szn/blob/main/src/server/server.zig#L1135), [`src/server/server.zig:1437`](https://github.com/cwt/szn/blob/main/src/server/server.zig#L1437), [`src/server/message_reader.zig:43`](https://github.com/cwt/szn/blob/main/src/server/message_reader.zig#L43)

> **Verification status:** found by static analysis during the 2026-10-05 audit.
> The control flow below was read from live source, but no runtime repro was
> constructed. Treat as a lead until reproduced.

## Problem

`MessageReader.buf` is an inline `[8192]u8` field of a heap-allocated
`MessageReader` (`message_reader.zig:43`), and `tryParse` returns a `Packet`
whose `data` slice points *into* it.

The `stdin_data` handler forwards that slice straight to the parser:

```zig
// src/server/server.zig:2592-2597
.stdin_data => {
    self.current_client_fd = fd;
    self.processInput(pkt.data) catch |err| { ... };
},
```

`processInput` then indexes the buffer per byte:

```zig
// src/server/server.zig:1437
const byte = buf[i];
```

and only re-checks the client at the **end** of `handleClient`. If a keybinding
mapped to `.detach` fires inside the same packet (e.g. `C-b d`), the action
reaches `removeClient(cfd)` (`:1135`), which destroys the reader:

```zig
self.allocator.destroy(entry.value);   // server.zig:2673
```

`processInput` then continues its `while (i < buf.len)` loop and reads freed
memory for every remaining byte of the packet.

The existing test sends only the two-byte `"\x02d"`, so `i == buf.len`
immediately after detach and the use-after-free is never exercised.

## Relationship to bug #428

#428 ("Use-after-free of MessageReader in handleClient packet loop") fixed the
*deferred `reader.consume(pkt)`* dereference after a handler freed the reader.
This is the same root cause reaching a different read site — the fix did not
cover the bytes `processInput` is still walking.

## Proposed Fix

Either copy `pkt.data` into a stack buffer before calling `processInput`, or
have `processInput` bail out as soon as the client is no longer registered:

```zig
if (!self.client_readers.contains(fd)) return;
```

at the top of each loop iteration. Add a test that sends a multi-byte packet
whose *trailing* bytes follow a detach binding.
