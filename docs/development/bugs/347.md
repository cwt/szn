# Bug 347 — `reflowCursorInternal` trims trailing empty screen lines during copy-mode entry, shifting visible grid down and corrupting prompt

### 347. Grid reflow trims trailing empty screen lines when scrollback history exists
**File:** `src/grid.zig:754-764`  
**Severity:** HIGH  
**Status:** ✅ FIXED  

### Problem
Running interactive applications (such as Antigravity CLI) inside `szn`, entering `copy-mode`, scrolling up, and then exiting `copy-mode` resulted in rendering glitches near the bottom of the screen where the input prompt was shifted down or layout corrupted.

### Root Cause
When entering copy-mode (`enterCopyMode`), `pane.forceReflow()` invokes `reflowCursorInternal` at the current window width (`new_width == self.width`).

`reflowCursorInternal` calculated `process_limit` by trimming trailing empty rows from the bottom of `self.lines` (the visible screen). When scrollback history was present (`hist_len > 0`), dropping trailing empty screen rows reduced the total line count to $H + V - E$.

During layout reconstruction:
1. `h_count` became $(H + V - E) - V = H - E$.
2. `self.history` received $H - E$ lines.
3. `self.lines` received the remaining $V$ lines, stealing $E$ lines from `self.history` to fill the top of the visible screen.

This shifted all visible screen content (including the input prompt) down by $E$ rows and prepended old scrollback lines to the top of the visible screen.

### Fix
In [`src/grid.zig`](file:///home/cwt/Projects/szn/src/grid.zig#L760-L764), updated `reflowCursorInternal` so that when reflowing at the same width with history present (`new_width == self.width and hist_len > 0`), `process_limit` is set to `total`. This guarantees that `self.lines` and `self.history` maintain their exact boundary and line counts without stealing scrollback history or shifting the screen.
