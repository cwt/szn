# Bug 501 — placeSixelImage errdefer leaks image bytes (latent)

### 501. Slot dropped, data not freed, markers/anchors left behind
**Severity:** LOW (latent — no live leak today, but a contract trap)
**Status:** 🟢 FIXED
**Files:** [`src/screen.zig:354-357`](../../../src/screen.zig)

## Problem

```zig
errdefer {
    self.sixel_images[slot] = null;
    self.sixel_refcounts[slot] = 0;
}
```

If a later `try self.grid.scrollUp()` (or similar fallible step) fails after the `SixelImage` (with its up-to-8 MiB `data` buffer) is installed, the errdefer drops the slot and zeroes the refcount **without freeing `SixelImage.data`** — and without rolling back any marker cells/anchors already placed. Today's callers free `dcs_bytes` themselves on error, so there is no live leak; but the ownership contract is a trap for the next caller, and partially-placed markers/anchors are left behind regardless.

## Proposed Fix

Free the image data inside the errdefer (deinit the `SixelImage` rather than just nulling the slot), and document the ownership contract: on error, `placeSixelImage` leaves no markers, no anchors, and no allocated image behind. Consider also rolling back already-placed marker cells.

## Resolution

- In `src/screen.zig`, updated `placeSixelImage`'s `errdefer` to deinitialize `sixel_images[slot]` (freeing `dcs_bytes`), zero the refcount, null the slot, and call `clearSixelMarkerCells(id)` to roll back any marker cells placed on the grid prior to error.
- Clarified ownership doc contract on `placeSixelImage` and `addSixelImage`.
- Removed redundant/duplicate `dcs_bytes` frees on error in `addSixelImage` and `flushPendingSixel` so `placeSixelImage` strictly manages ownership of `dcs_bytes`.
- Added unit test in `src/screen.zig` testing that `placeSixelImage` frees image bytes, zeroes slot/refcount, and cleans up marker cells when an error occurs during grid scrolling.
