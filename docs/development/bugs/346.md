# Bug 346 — I/O functions do not receive `io: std.Io` parameter (Zig 0.16 rule #2)

### 346. Missing `io` capability in I/O functions
**Files:** `src/main.zig`, `src/server/server.zig`, `src/server/pty.zig`, `src/server/loop.zig`, `src/tty/tty.zig`, `src/client/client.zig`, `src/client/connect.zig`, `src/client/raw.zig`
**Severity:** MEDIUM
**Status:** 🔓 OPEN

Zig 0.16 rule #2 states: *"I/O needs `io`"* — every function that performs I/O must receive `io: std.Io` as a parameter. The migration table says:

| Old (do not use) | New (0.16) |
|---|---|
| `std.fs.cwd().openFile(path, .{})` | `std.Io.Dir.cwd().openFile(io, path, .{})` |
| `std.fs.cwd().readFileAlloc(allocator, path, max)` | `std.Io.Dir.cwd().readFileAlloc(io, path, gpa, .limited(max))` |
| `file.close()` | `file.close(io)` |
| `std.time.sleep(ns)` | `try std.Io.sleep(io, .fromNanoseconds(ns), .awake)` |
| `std.net.*` | `std.Io.net.*` via `io` |

**Current state:** The codebase uses raw C syscalls (`std.c.read`, `std.c.write`, `std.c.poll`, `std.c.pipe`, `std.c.close`, etc.) throughout, which bypass the `std.Io` capability system entirely. This is a pragmatic choice for a terminal multiplexer that needs direct POSIX access, but it means the code is not compliant with the 0.16 I/O capability model.

**Specific violations:**

| File | Function | Missing `io` |
|---|---|---|
| `src/main.zig` | `writeAll(fd, buf)` | `io` for write |
| `src/main.zig` | `writeServer(fd, buf)` | `io` for write |
| `src/main.zig` | `flushStdout(fd, out_buf)` | `io` for write |
| `src/main.zig` | `waitForSocket()` | `io` for sleep (usleep) |
| `src/main.zig` | `runInteractiveClient(allocator)` | `io` for poll, read, write |
| `src/server/loop.zig` | `Loop.run(...)` | `io` for poll |
| `src/server/pty.zig` | `Pty.readOutput(...)` | `io` for read |
| `src/server/pty.zig` | `Pty.writeInput(...)` | `io` for write |
| `src/tty/tty.zig` | `Term.write(...)` | `io` for write |
| `src/client/client.zig` | `fdRead(fd, buf)` | `io` for read |
| `src/client/client.zig` | `fdWrite(fd, buf)` | `io` for write |

**Fix approach:** Because this codebase relies heavily on raw POSIX syscalls (which is appropriate for a tmux-like program), the practical fix is to thread `io: std.Io` through the top-level entry points (`main`, `Server.run`, `Loop.run`) and pass it down to any function that uses `std.Io.*` APIs. Pure C-syscall wrappers (like `writeAll`, `fdRead`) can remain as-is since they operate on raw fds — but any function that calls `std.Io.Dir`, `std.Io.sleep`, or `std.Io.Mutex` must receive `io`.

**Priority:** This is a structural compliance issue, not a runtime bug. The program works correctly with raw C syscalls. The fix is a signature-wide threading change.
