# Bug 522 — `behind` is never cleared on backlog drop

### 522. Force-dropping the out-buffer leaves the client marked behind forever
**Severity:** MEDIUM
**Status:** ✅ FIXED
**Files:** [`src/server/server.zig:2830-2837`](https://github.com/cwt/szn/blob/main/src/server/server.zig#L2830-L2837), [`src/server/server.zig:2766-2772`](https://github.com/cwt/szn/blob/main/src/server/server.zig#L2766-L2772), [`src/server/server.zig:2890`](https://github.com/cwt/szn/blob/main/src/server/server.zig#L2890)

> **Verification status:** the logic was read from live source and the state
> machine is unambiguous; the *reachability* (a client accumulating >16 MiB
> behind) was not demonstrated. Treat as a lead until reproduced.

## Problem

When a display client falls far enough behind, the server abandons its backlog:

```zig
// src/server/server.zig:2830-2837
if (dc.out_buf.items.len + total_len > MAX_OUT_BUF) {
    _ = self.flushDisplayClient(dc);
    if (dc.out_buf.items.len + total_len > MAX_OUT_BUF) {
        dc.out_buf.clearRetainingCapacity();
        dc.last_cells.clearRetainingCapacity();
        return false;
    }
}
```

The drop path clears `out_buf` and `last_cells` but leaves `dc.behind == true`
and `behind_count` set. That combination deadlocks the client:

* Next render, `out_buf.items.len == 0`, so the top-of-loop
  `flushDisplayClient` is skipped.
* `writeFrameToClient` short-circuits on `if (dc.behind) return true;`
  (`:2890`) and writes nothing.
* `if (dc.behind or !self.flushDisplayClient(dc)) all_flushed = false;`
  (`:3352`) short-circuits on the first term, so `flushDisplayClient` is never
  called and `behind` can never clear.

The result is that `all_flushed` stays false permanently, `self.dirty` is never
cleared, and that client never receives another frame — even after it drains.
`appendClientOutUrgent` (`:2764`) has the same omission.

## Proposed Fix

When dropping the backlog, clear the flag in the same step:

```zig
if (dc.behind) {
    dc.behind = false;
    self.behind_count -|= 1;
}
```

and, if no client remains behind, call `resumePaneReads()`. Factor the cap check
into one helper so both `appendClientOut` variants share it (see bug #520,
site 1).

## Fix

Both backlog-drop sites now clear the flag through one helper:

```zig
// src/server/server.zig
fn clearBehind(self: *Server, dc: *DisplayClient) void {
    if (dc.behind) {
        dc.behind = false;
        self.behind_count -|= 1;
    }
}
```

called from `appendClientOutUrgent` and from the render-path drop. The saturating
decrement matches every other `behind_count` site (`server.zig:2999`), so a stale
flag can never underflow the counter and make `anyDisplayClientBehind()` lie.

No separate "resume reads" call is needed: the event loop already gates pane
reads on `behind_count > 0`, so decrementing to zero resumes them.

## Regression test

`clearBehind resets the flag and the counter — bug #522` (`src/server/server.zig`)
puts a client behind, clears it, and asserts the flag and counter are both reset,
then clears again to pin the idempotent/underflow-guard behaviour.

The drop *sites* themselves need a >16 MiB backlog (`MAX_OUT_BUF = 16 << 20`) to
reach, which is too heavy for this suite's shared `DebugAllocator` budget, so
they are covered by inspection rather than by a test that fills the buffer.

Verified with the full suite on **Zig 0.16.0 and 0.17.0**: 1053/1053 passing on
both.
