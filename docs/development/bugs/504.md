# Bug 504 — libthai loader and break context lack thread-safety synchronization (latent)

### 504. Unsynchronized global state and shared ThBrk pointer
**Severity:** LOW (latent — safe under single-threaded server architecture)  
**Status:** 🔴 OPEN  
**Files:** [`src/thai.zig:436-498`](../../../src/thai.zig#L436-L498)

## Problem

In [`src/thai.zig`](../../../src/thai.zig), dynamic loading of `libthai` is handled via mutable module globals:

```zig
var libthai_instance: ?LibThai = null;
var libthai_tried = false;

pub fn getLibThai() ?*const LibThai {
    if (!libthai_tried) {
        libthai_tried = true;
        initLibThai();
    }
    if (libthai_instance) |*inst| return inst;
    return null;
}
```

Furthermore, [`initLibThai`](../../../src/thai.zig#L439) allocates a single global `ThBrk*` word-breaker context handle (`brk = th_brk_new(null)`), and [`findWordBreaks`](../../../src/thai.zig#L500) executes `libthai.th_brk_wc_find_breaks(libthai.brk, ...)` directly on this shared instance.

### Concurrency Risk:
- Neither `getLibThai()` nor `initLibThai()` uses atomic flags or a mutex.
- `th_brk_wc_find_breaks` is not documented to be re-entrant when sharing the same `ThBrk` handle concurrently.
- Today, `szn` runs an event-driven, single-threaded server loop ([`src/server/loop.zig`](../../../src/server/loop.zig)). All terminal handling and grid reflow happen synchronously on the server thread, so this is currently latent.
- However, if asynchronous pane background rendering, parallel reflow, or off-thread terminal processing are introduced, this shared state will become a data race.

## Proposed Fix

1. Add thread-safety documentation clarifying that `libthai_instance` and `ThBrk` are explicitly single-threaded and bound to the server thread lifecycle.
2. If multi-threaded reflow or background workers are introduced in the future:
   - Guard `getLibThai()` with `std.once` or atomic initialization.
   - Allocate `ThBrk` per-thread or pass a local context into `th_brk_wc_find_breaks`.
